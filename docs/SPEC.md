## 1. 목적과 설계 원칙

### 목적

1. **주간 공지 자동화** — 지금 메모장에 수기로 쓰는 공지를 시트 입력만으로 생성
2. **월별 아카이브** — 언제 무슨 곡을 불렀는지, 파트별 몇 명이 섰는지 누적
3. **성가곡 pool** — 보유 악보집 수록곡을 후보 리스트로 관리, 다음 선곡의 근거로 사용
4. **연습 자료 상시 접근** — 파트별 영상을 곡 단위로 묶어 보관

### 원칙

- **일상 편집은 구글 시트에서 한다.** 웹앱에 범용 편집 폼을 만들지 않는다. 편집자가 5명 이내이고 모두 시트에 익숙하므로, 인증·권한·쓰기 실패 처리를 상시로 떠안을 이유가 없다.
- **예외는 월간 선곡 하나.** 곡 pool 탐색·중복 확인·공지 생성이 한 화면에서 끝나야 의미가 있는 작업이라, 여기만 쓰기 경로를 연다. 그마저도 붙여넣기 방식(§12.1)을 먼저 쓰고, 필요가 확인되면 쓰기 엔드포인트(§12.2)로 승급한다.
- **열 위치가 아니라 헤더 이름으로 파싱한다.** 5명이 동시에 만지면 열 삽입·삭제가 반드시 일어난다. 헤더 행은 시트에서 보호를 건다.
- **자동 수집한 데이터는 초안이지 사실이 아니다.** 반드시 `검증` 플래그를 거쳐야 대원에게 노출된다. (근거는 §9.3)
- **모바일 우선.** 접속의 대부분은 카톡 링크를 통한 폰 접속이다.
- **오프라인 내성.** 주일 아침 교회 와이파이가 불안정할 수 있으므로 마지막 응답을 localStorage에 캐시하고, 네트워크 실패 시 캐시를 보여준다 (stale-while-revalidate).

## 2. 아키텍처

```
Google Sheets (단일 파일, 7 데이터 시트 + N개 연도 뷰 탭)
      │
      │  Apps Script 웹앱 (doGet → JSON, 읽기 전용)
      ▼
  단일 JSON 엔드포인트
      │  fetch + localStorage 캐시
      ▼
GitHub Pages (React SPA, 정적)
```

**연동 방식: Apps Script 웹앱 JSON 엔드포인트**

| 방식 | 채택 | 이유 |
|---|---|---|
| Apps Script `doGet` → JSON | ✅ | 6장을 한 번의 요청으로, 캐시 지연 없이 즉시 반영. 스크랩·API 키를 서버측에 숨길 수 있음 |
| 시트 "웹에 게시" → CSV | ❌ | 최대 5분 캐시. 주일 아침 링크 수정이 바로 안 보임. 시트당 1요청 = 6요청 |
| GitHub Actions로 JSON 스냅샷 커밋 | 🔜 | 안정성은 최고지만 반영 지연. 트래픽/장애 문제가 생기면 그때 승급 |

배포 설정: 실행 주체 `나`, 액세스 권한 `모든 사용자`. 시트 자체는 비공개로 유지된다.
Apps Script는 `script.googleusercontent.com`으로 302 리다이렉트하며 CORS 헤더를 포함하므로 GitHub Pages에서 `fetch` 가능.

**응답 형태 (단일 요청)**

```json
{
  "updatedAt": "2026-09-03T10:00:00Z",
  "books": [], "songs": [], "services": [],
  "rehearsals": [], "practiceLinks": [], "config": {}
}
```

`yt_cache`는 내부용이라 응답에 포함하지 않는다.

**스택**: Vite + React + TypeScript + Tailwind. 빌드 산출물을 GitHub Pages에 배포. 서버 비용 0.

## 3. 연도 관리 방식

### 결론: 저장은 평면, 조회는 연도 뷰 탭

연도별로 **별도 스프레드시트 파일**을 만들고 그 안에 월별 탭을 두는 방식은 채택하지 않는다.

| 문제 | 내용 |
|---|---|
| **드롭다운이 파일 경계를 못 넘음** | `songs` pool은 연도 무관 마스터인데 선곡 입력은 연도 파일에서 한다. 구글 시트 데이터 유효성 검사는 타 파일 범위를 직접 참조 불가 → IMPORTRANGE 필요 → 파일마다 승인 재수행, 재계산 지연, 잦은 `#REF!`. **곡명 오타 방지라는 설계 중심이 무너진다.** |
| **연말/연초 경계** | 12월 말 연습이 1월 첫 주 찬양을 위한 것이면 `rehearsals`→`services` 외래키가 파일을 넘는다 |
| **크로스이어 조회가 앱의 핵심** | "이 곡 언제 불렀지", "작년 성탄절 선곡", "부활절 후보" 모두 전 연도 스캔. 새 해마다 스프레드시트 ID를 스크립트에 추가하고 재배포해야 함 |
| **백업·권한 리스크** | 파일이 N개면 삭제·권한 단절 지점이 N개 |
| **분량은 이유가 안 됨** | 연 60회 × 10년 = `services` 600행, `practice_links` 3,000행. 시트 한도는 1,000만 셀 |

### 대신 이렇게 한다

**저장** — 단일 스프레드시트, 평면 테이블. 날짜 열이 이미 연/월을 담고 있다.

**시트 안 연도별 보기** — `2026` 같은 탭을 만들고 A1에 한 줄:

```
=QUERY(services!A:N, "select * where year(A)=2026 order by A", 1)
```

자동으로 채워지고, 읽기 전용이고, 월 구분 소계도 붙일 수 있다. 새 해엔 탭 복제 후 숫자만 바꾼다.
이 탭들은 Apps Script가 JSON으로 내보내지 않는다 (화이트리스트 방식으로 데이터 시트만 지정).

**앱에서의 연도/월 보기** — §6.2 월별 아카이브 화면이 그 역할.

**진짜 분리가 필요해질 때** — 총무 인수인계나 10년 뒤 정리 시점에, 스크립트로 특정 연도를 별도 파일에 스냅샷 내보내기. **아카이브 사본이지 운영 데이터가 아니다.**

## 6. 화면 명세

### 6.1 홈 — 다가오는 찬양일

가장 중요한 화면. 대원 입장에서 필요한 건 사실상 이것뿐이다.

- 다가오는(또는 가장 최근) 찬양일 카드
- 곡 제목 + 출처(중47-03)
- 연습 일정 목록
- **파트 버튼 6개** — 탭하면 유튜브 앱/새 탭으로 열림
- **`공지 복사` 버튼** — 기존 포맷 그대로 클립보드에 복사

> 유튜브 썸네일만으로는 어느 파트인지 분간이 안 된다. 파트 라벨을 크게, 썸네일은 보조로.

### 6.2 월별 아카이브

`2026년 9월` 형태로 접히는 목록. 찬양일마다 곡, 파트별 인원 (`S8 A7 T4 B5 · 총24`), 세션, 기록영상 링크.

### 6.3 곡 라이브러리 (pool)

검색 + 필터: 악보집 / 절기 / 성부 / 상태 / 난이도 / 검증여부.
부른 이력이 있는 곡은 `마지막 2025-12-24` 표시. 미검증(`검증=FALSE`) 항목은 흐리게 + 배지.

### 6.4 서가 뷰

`표지색`으로 칠한 책등 카드를 권 번호순으로. 탭하면 해당 집 수록곡. 미보유 권은 빈 슬롯으로.

### 6.5 곡 상세

제목 / 원제 / 작곡·편곡 / 출처 / 절기 / 난이도 / 악보 링크 / 파트별 영상 임베드 / **이 곡을 부른 날짜 이력**.

### 6.6 통계 (Phase 4)

월별 총인원 추이, 파트별 평균, 절기별 선곡 분포.

### 6.7 월간 선곡 (Planner) — 핵심 기능

이 화면의 진짜 가치는 공지 자동 생성이 아니라 **중복 선곡 방지**다.
"작년에 부른 곡을 기억 못 하고 다시 고르는" 실수를 데이터로 막는다.

**흐름**

```
1. 대상 월 선택            2026년 10월
2. 찬양일 자동 생성        10/4, 10/11, 10/18, 10/25 (+ 특별예배 수동 추가)
3. 찬양일마다 곡 선택      songs pool에서 고름
4. 연습 일정 자동 제안     직전 주일 13:30 / 수요일 20:00 (config 기본 패턴, 수정 가능)
5. 결과 출력               찬양일별 공지 텍스트 + 시트 붙여넣기 블록
```

**곡 선택 UI에 반드시 표시할 것**

| 표시 | 데이터 출처 | 이유 |
|---|---|---|
| **마지막으로 부른 날** | `services` 역참조 | 중복 방지의 핵심 |
| **최근 12개월 내 경고** | 동상 | 붉은 배지 + 날짜 |
| 파트 영상 보유 | `practice_links` 개수 | 없으면 연습 자료를 직접 만들어야 함을 선택 시점에 인지 |
| 검증 상태 | `songs.검증` | 미검증 곡은 흐리게 |
| 절기 힌트 | `config` 월→절기 매핑 | 10월 → 추수감사 제안 |
| 난이도 | `songs.난이도` | 한 달에 어려운 곡이 몰리지 않게 |

**절기 자동 제안**은 1차에서는 월→절기 힌트 매핑 테이블로 충분하다.
사순·부활 같은 이동축일 계산은 P4로 미룬다.

**공지 출력 단위**: 선곡은 월 단위로 하되, **공지는 찬양일별로 뽑는다.**
기존 운영이 주별 공지이기 때문이다. 월 전체 요약본도 함께 생성한다.

```
(소프라노)

```

### 7.1 곡 수에 따른 템플릿 분기

기존 메모 형식은 **곡이 정확히 하나**라는 전제 위에 있다. 곡명 없이 파트 블록만 나열하므로,
2곡 이상이면 링크 세트가 여러 벌 나오면서 어느 것이 어느 곡인지 구분할 수 없다.

곡 수에서 **자동으로** 분기한다. `config` 설정이 아니라 파생값이다 — 총무가 매번 판단할 일이 아니다.

**1곡 (기본)** — 위 형식 그대로. 대원들이 익숙한 포맷을 건드리지 않는다.

**2곡 이상 (특별예배)** — 번호 붙은 곡명 헤더를 강제 삽입한다. `공지_곡목표시` 설정과 무관하게 항상 표시.

```
12월 25일 성탄 찬양
<성가연습 일정>
21일 주일 1시 30분
24일 수요일 8시
1. (곡명)
(합창)
https://youtu.be/...
(소프라노)
https://youtu.be/...
2. (곡명)
(합창)
https://youtu.be/...
```

> 선곡 화면(§6.7)도 같은 원칙을 따른다. 슬롯 3개를 나란히 보여주지 말고 기본은 한 칸 + "곡 추가" 버튼.
> 3개가 기본인 것처럼 보이면 안 하던 것을 하게 된다.

### 7.2 공통 규칙

- 시각은 `13:30` → `1시 30분`, `20:00` → `8시` (정각은 분 생략)
- 연습일은 일(日)만, 요일은 `구분` 열 값 사용
- 링크 없는 파트는 블록 자체 생략
- `검증=FALSE`인 링크는 공지에서 제외하고 화면에 경고 표시 (§9.3)
- `공지_곡목표시`가 TRUE면 제목 아래 곡명 한 줄 추가
- 클립보드 복사 실패 시(iOS Safari 등) 텍스트 영역을 펼쳐 수동 복사 유도

## 8. URL 정규화

시트에 어떤 형태로 붙여넣어도 동작해야 한다.
기존 메모의 `?is=...`(`?si=`의 오타로 추정)처럼 깨진 파라미터도 무시.

**입력 허용**: `youtu.be/{id}`, `youtube.com/watch?v={id}`, `youtube.com/shorts/{id}`, `m.youtube.com/...`, 임의 쿼리 파라미터 포함

**추출**: 영상 ID 11자 `[A-Za-z0-9_-]{11}`

**출력**

- 공유용: `https://youtu.be/{id}` (시작초 있으면 `?t={n}`)
- 임베드: `https://www.youtube.com/embed/{id}?start={n}`
- 썸네일: `https://img.youtube.com/vi/{id}/hqdefault.jpg`

ID 추출 실패 시 원본 URL을 그대로 링크로 두고 목록에서 경고.

### 9.3 왜 `검증` 플래그가 필수인가 (실증)

나무위키 41집 표의 유튜브 링크가 **18집 표의 링크 ID와 동일**하다.
편집 과정에서 복사된 오류로 보인다. 이걸 그대로 쓰면 대원들에게 엉뚱한 곡의 파트 영상이 배포된다.

공식 채널을 1순위로 올리면 이 오류 계열은 사라지지만(출판사 자신의 채널이므로),
**제목 매칭이 틀릴 가능성은 남는다.** 따라서 검증 게이트는 그대로 유지한다.

- 자동 수집된 모든 행은 `검증 = FALSE`로 삽입
- `검증 = FALSE`인 링크는 **공지 텍스트에서 제외**
- 앱 UI에서 미검증 항목은 흐리게 + "미확인" 배지
- 총무/지휘자가 재생 확인 후 TRUE로 전환
- 자동 수집은 기존 행을 덮어쓰지 않는다 (append only, 중복은 `곡코드`로 skip)

### 9.4 채널 미러링 방식

곡마다 검색하지 않는다. **채널 전체를 `yt_cache`에 한 번 미러링한 뒤 로컬에서 매칭한다.**

**API 비용 구조가 이 설계를 결정한다.**

| 호출 | 비용 | 용도 |
|---|---|---|
| `search.list` | **100 units** | 곡별 검색 (지양) |
| `channels.list` | 1 unit | 핸들 → 채널 ID |
| `playlists.list` | 1 unit / 50개 | 집별 재생목록 열거 |
| `playlistItems.list` | 1 unit / 50개 | 재생목록 내 videoId + 제목 |

채널 전체를 훑어도 수십 units. 일일 할당량 10,000에 한참 못 미친다.

**이 구조의 핵심 이점: 매칭 규칙을 틀려도 공짜로 다시 돌릴 수 있다.**
영상 제목 형식은 아직 확정할 수 없다(유튜브 페이지가 스크립트 렌더링이라 사전 확인 불가).
규칙은 실제 데이터를 한 번 받아본 뒤 정해야 하는데, 캐시가 시트에 있으면 규칙만 고쳐
로컬 재매칭하면 된다. 곡별 검색이었다면 규칙을 고칠 때마다 할당량을 다시 태웠을 것이다.

**동작 순서**

```
[1단계] 채널 미러링  — 메뉴: 성가 아카이브 > 채널 동기화
  channels.list(forHandle=JandAArt) → channelId
  playlists.list(channelId) 전체 페이지 순회
  각 재생목록마다 playlistItems.list 전체 페이지 순회
  → yt_cache에 upsert (videoId 기준)

[2단계] 매칭       — 메뉴: 성가 아카이브 > 영상 매칭
  재생목록명에서 집 번호 추출  (예: "중앙성가 41집" → 중41)
  영상 제목에서 곡번호·곡명·파트 추출   ※ 규칙은 1단계 결과를 보고 확정
  1순위: 집번호 + 곡번호 일치
  2순위: 집번호 + 곡명 정규화 일치
  → practice_links에 append (출처=youtube_channel, 검증=FALSE)
  → 매칭 실패 목록을 별도 리포트로 출력

[3단계] 검증       — 사람이 재생 확인 후 검증=TRUE
```

**제목 정규화 규칙** (매칭 전 양쪽에 동일 적용)

- 대괄호·소괄호 안 채널 태그 제거 (`[중앙아트]` 등)
- 공백·중점·하이픈·따옴표 제거
- 전각/반각 통일, 숫자 앞 0 제거

**신규 악보집 등록** — 메뉴: `성가 아카이브 > 악보집 등록`

```
1. 권 번호 입력 (예: 50)
2. books에 행 생성 — 집코드 `중50` 자동 부여
3. yt_cache에서 해당 집 재생목록 탐색 → 수록곡 목록 확보
4. 실패 시 폴백: joongangart.kr 목록 페이지 → 나무위키 → 목차 텍스트 붙여넣기 대화상자
   (한 줄에 `번호<탭>곡명` 또는 `번호. 곡명` 형식 모두 허용)
5. songs에 append — 곡코드 자동, 상태=후보, 검증=FALSE, 출처 기록
6. 2단계 매칭 실행 → practice_links 채움
7. 리포트: N곡 추가, M개 영상 매칭, 실패 K건, 전부 검증 대기
```

**곡코드 규칙은 확장에 열려 있다.** `{집코드}-{수록번호}` 형식이라 새 권이든
새 시리즈(여성성가, Best 등)든 `books`에 행만 추가하면 코드 수정이 필요 없다.

**API 키**는 Apps Script Properties에 저장한다. 서버측이라 프론트엔드에 노출되지 않는다.

**41집 이후 공식 파트연습실**: 41집부터 중앙아트가 파트별 음원을 MIDI와
박신화콰이어 녹음 두 형태로 제공한다. 보유 41·43·47집이 여기 해당한다.

### 9.5 초기 데이터 입력 전략

11권 × 권당 30곡 내외 ≈ **300곡 이상**. 손으로 치면 프로젝트가 여기서 멈춘다.

**권장 순서**

1. `books` 11행만 먼저 등록 → **앱을 띄우고 바로 쓰기 시작**
2. 채널 미러링 1회 실행 → `yt_cache` 확보. 여기서 보유 11권 중 재생목록이 있는 집을 확인
3. 재생목록이 있는 집부터 자동 백필 (전부 검증 대기)
4. 재생목록이 없는 집은 나무위키 표 → joongangart.kr 목록 페이지 → 목차 OCR 순으로 보충
5. 그래도 남는 집은 **실제로 선곡할 때마다 그 곡만 추가** — pool은 시간이 지나며 채워진다

> 아카이브와 공지 기능은 1번만 끝나면 즉시 동작한다. 곡 pool 완성은 앱 가동의 전제 조건이 아니다.

| **P3** | 곡 라이브러리 + 서가 뷰 + 필터 + 검증 배지 | "부활절 후보곡"을 필터로 뽑는다 |
| **P3.5** | 채널 미러링 + 매칭 + 악보집 등록 스크립트 (§9.4) | 채널 동기화 1회 후, 권 번호만 넣으면 수록곡과 파트 영상이 검증 대기 상태로 들어온다 |
| **P4** | 쓰기 엔드포인트(§12.2), 통계, PWA, 오프라인 캐시 | 선곡 저장이 시트에 바로 반영된다. 와이파이 없이 마지막 공지가 뜬다 |

## 12. 시트 쓰기 경로

월간 선곡 결과를 `services`·`rehearsals`에 반영하는 방법. **두 단계로 나눠 도입한다.**

### 12.1 붙여넣기 블록 (P2, 먼저 구현)

선곡을 마치면 두 가지를 복사 버튼으로 제공한다.

1. **공지 텍스트** — 찬양일별 (§7 포맷 그대로)
2. **시트 붙여넣기 블록** — 탭 구분 텍스트. `services`용 N행, `rehearsals`용 M행

총무가 시트를 열고 마지막 행에 붙여넣으면 끝난다.

| 장점 | 내용 |
|---|---|
| 인증 불필요 | 공개 엔드포인트에 쓰기 통로를 열지 않는다 |
| 구현이 가볍다 | 클립보드 API + 문자열 조립이 전부 |
| **12.2의 폴백이 된다** | 쓰기가 네트워크·권한 문제로 실패해도 선곡 작업이 날아가지 않는다 |

마지막 항목이 핵심이다. 12.2를 나중에 만들더라도 이 경로는 남겨둔다.

### 12.2 쓰기 엔드포인트 (P4, 필요가 확인되면)

`doPost` + 편집자 공유 키.

```
클라이언트: 앱에 공유 키 1회 입력 → localStorage 저장
요청:      POST { key, action: "appendService", payload: {...} }
스크립트:  1) 키 검증
           2) 페이로드 검증 — 곡명이 songs에 실재하는지, 찬양일 중복 아닌지
           3) append only (기존 행 수정·삭제 불가)
           4) 결과 반환. 실패 시 클라이언트는 12.1 붙여넣기 블록으로 폴백
```

**위협 모델 판단**: 공유 키가 클라이언트에 있으므로 완벽한 보안은 아니다.
다만 대상이 교회 성가대 일정 시트이고, 구글 시트는 전체 버전 기록이 남아 잘못된 쓰기를
되돌릴 수 있다. append만 허용하므로 기존 기록이 훼손되지 않는다. 이 수준이면 충분하다.

**주의**: 앱에서 쓰면 시트의 데이터 유효성 검사(드롭다운)를 우회하게 된다.
따라서 곡명 실재 여부 검증을 Apps Script 쪽에서 반드시 수행한다.

**읽기 엔드포인트는 그대로 공개로 둔다.** 대원들이 카톡 링크로 로그인 없이 여는 흐름이
깨지면 안 된다. 읽기와 쓰기는 별개 배포로 분리한다.

## 13. GitHub Pages 배포 제약

정적 호스팅이라 서버 설정이 없다. 구현 시 반드시 부딪히는 지점 세 가지.

### 13.1 base path

Vite 설정에 저장소명을 넣지 않으면 자산 경로가 전부 깨진다. GitHub Pages에서 가장 흔한 첫 실패.

```js
// vite.config.ts
export default defineConfig({ base: '/choir-archive/' })
```

커스텀 도메인을 붙이면 `base: '/'`로 되돌린다.

### 13.2 라우팅 — HashRouter 사용

Pages에는 서버 리라이트가 없다. 클라이언트 라우팅을 쓰면 새로고침과 딥링크가 404가 난다.

`404.html`을 `index.html` 사본으로 두는 우회법도 있지만, **HashRouter**(`#/archive/2026-08`)를 쓴다.
더 단순하고 카톡 인앱 브라우저에서도 안정적이다. URL이 덜 예쁜 것은 이 앱에서 문제되지 않는다.

### 13.3 저장소 공개 여부와 비밀 관리

비공개 저장소에서 Pages를 쓰려면 유료 플랜이 필요하다. **공개 저장소를 권한다.**

| 항목 | 저장소에 둬도 되는가 | 이유 |
|---|---|---|
| Apps Script **읽기** URL | ✅ | 앱을 여는 사람의 브라우저에 어차피 노출된다. 데이터에 개인정보가 없다(§4.3에서 참석을 숫자로만 기록한 결정이 여기서 값을 한다) |
| YouTube Data API 키 | ❌ | Apps Script Properties에 보관. 프론트엔드는 유튜브 API를 직접 호출하지 않는다 |
| **§12.2 쓰기 공유 키** | ❌ **절대 불가** | 사용자가 앱에 직접 입력해 브라우저 localStorage에만 남긴다. 저장소·빌드 산출물 어디에도 넣지 않는다 |

### 13.4 배포

`main` 푸시 시 GitHub Actions가 빌드 후 Pages에 배포. 빌드 산출물을 커밋하지 않는다.
